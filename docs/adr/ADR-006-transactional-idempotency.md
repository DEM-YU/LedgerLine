# ADR-006: 幂等键与业务写入同一事务

状态：已采纳

## 背景

客户端重试、网络超时或并发重复提交记账/导入/确认匹配请求时，系统必须保证写操作最多生效一次，且不能出现“记录了幂等键但业务未落库”或“业务已落库但幂等响应丢失”的中间状态。

## 选项

1. **Redis 或独立事务预占位幂等键**：不阻塞业务事务，但存在崩溃窗口期（状态半完成），需要复杂的补偿和租约清理。
2. **PostgreSQL `idempotency_keys` 表同事务写入**：以 `(org_id, endpoint, key)` 为主键，在业务同一个数据库事务内插入幂等键并最终写回 `response_code` 和 `response_body`。

## 决定

采用选项 2：

- 所有写接口接收 `Idempotency-Key` 请求头。
- 请求进入事务后立即尝试插入或锁定 `idempotency_keys` 对应记录：若同键并发到达，第二个请求在唯一约束/行锁上等待第一个事务提交；若已存在记录且 `request_hash` 一致，直接重放原响应；若 `request_hash` 不一致，返回 `422`。
- 过期幂等键由后台 Worker 定期清理。

## 后果

- 优点：彻底消除半完成状态，无需额外分布式锁或状态机修复逻辑。
- 代价与限制：同一 `Idempotency-Key` 在长事务提交期间并发到达时，后续请求会被阻塞等待至首个事务结束或超时，因此写事务本身必须保持简短（耗时解析与批量对账交由异步 `jobs` 处理）。
