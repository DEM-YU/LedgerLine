# ADR-004: 后台任务基于 PostgreSQL `jobs` 表与 `SKIP LOCKED`

状态：已采纳

## 背景

银行对账单异步导入解析、自动对账、报表物化、余额全量校验以及过期幂等键清理需要在后台可靠执行，并与业务数据库状态保持一致性。

## 选项

1. **引入 Redis + Celery / ARQ**：吞吐上限高，但需要额外运维组件，且任务入队与业务数据库提交之间存在“双写不一致”风险（业务回滚但任务已入队，或业务提交但入队失败）。
2. **PostgreSQL `jobs` 表 + `SELECT ... FOR UPDATE SKIP LOCKED`**：任务入队与业务写入在同一个数据库事务内完成，Worker 通过 `SKIP LOCKED` 竞争领取任务，配合租约超时（lease timeout）与指数退避重试。

## 决定

采用选项 2，不引入 Redis：

- 新增 `jobs` 表，记录任务类型、载荷、状态、尝试次数、`lease_expires_at`、`next_run_at` 及错误详情。
- 所有任务处理函数必须设计为幂等，超时未完成或失败按指数退避重试，超过最大重试次数进入 `dead` 状态。

## 后果

- 优点：少维护一套中间件，入队与业务状态原子提交（天然实现 Transactional Outbox 语义），测试环境只需启动 PostgreSQL 即可验证全链路。
- 代价与限制：基于轮询与行锁的队列吞吐上限低于专用消息队列；若任务量远超中小微企业记账场景需另行演进，但当前阶段足够且可控。
