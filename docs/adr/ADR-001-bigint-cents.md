# ADR-001: 金额统一使用 `bigint` 分，Python 侧用 `Decimal` 换算

状态：已采纳

## 背景

复式记账与银行对账要求绝对精确的算术运算。即使 `1` 分钱的舍入误差也会导致试算不平、银行余额连续性校验失败以及对账漏配或错配。系统固定使用单一币种 `CAD`（最小单位为分，`1 CAD = 100 cents`）。

## 选项

1. **浮点数（`float` / `DOUBLE PRECISION`）**：二进制浮点无法精确表示十进制小数（如 `0.1 + 0.2 != 0.3`），累计求和会产生不可控漂移。
2. **数据库 `NUMERIC(p, s)` + Python `Decimal`**：可精确表示十进制小数，但存在标度（scale）不一致、序列化开销以及 Python 端比较/JSON 规范化复杂度。
3. **数据库 `bigint` 存储整数分 + 正整数金额配合显式借贷方向（`'D'` / `'C'`）**：输入解析阶段用 `Decimal` 严格校验两位小数后换算为整数分，全链路持久化与算术均以整数执行。

## 决定

采用选项 3：

- 数据库中所有金额字段统一为 `bigint`（单位：分），分录行约束 `CHECK (amount_cents > 0)`，借贷方向由 `side IN ('D', 'C')` 显式表达。
- Python 仅在解析外部输入（CSV 金额列、API 请求）与格式化输出时使用 `Decimal`，不得将 `float` 引入任何计算路径，也不向数据库存储浮点或小数字段。

## 后果

- 优点：加减求和完全精确且无溢出/精度丢失风险；`canonical_json` 哈希序列化可直接输出整数，避免 `"10.00"` 与 `"10.0"` 等规范化歧义；整数比较与聚合性能优于 `NUMERIC`。
- 代价与限制：API 展示层与导出层需负责分的格式化；若未来扩展支持不同小数位数的多币种（当前范围明确排除），需补充币种最小单位映射表。
